# オーラコネクト・バトル

オーラ(玉)をつないで消し、仲間と共にダンジョンを攻略するブラウザ/PWA のパズルRPG。
ビルド不要の静的サイトで、ES Modules をそのまま読み込んでいる。

画面モジュールと相互参照しない。

## ゲームの主なルール

### 編成は「人物」4人
自陣は**人物キャラクター3人**(先頭がリーダー)と、ダンジョン出発時に選ぶ
**サポート1人**の計4人。サポートはフレンドの貸し出しキャラに加えて、
**NPCサポート**をいつでも選べる(フレンドがいなくても困らない)。
NPCサポートはプレイヤーランクで順次解放される。

編成は**5つのプリセット**(`state.teams`)として保存でき、`state.teamIndex` が
いま選んでいるものを指す。バトルへ出るのは `activeTeam()`。

### キャラクター画面は5つのページ
ホーム → キャラクター で入口を5枚出し、そこから各ページへ潜る。

| ページ | 一覧アイコンに重ねるもの | 選んだときに出す詳細 |
|---|---|---|
| 編成 | 編成中の枠(リーダー / サブ) | 枠のタップで手持ち一覧 → 入れ替え |
| 強化・進化 | ★ ・ Lv ・ 所持数 ・ 進化可 | 立ち絵 / レベル / ステータス / 強化 / 進化 |
| 開眼 | ★ ・ Lv ・ 🔸の段階 | 立ち絵 / 開眼の段階 / 必要な素材 |
| 送還 | ★ ・ Lv ・ 所持数 ・ 編成中 | 送還する数のモーダル(初期値は所持数) |
| 図鑑 | (アイコン一覧ではなくカード) | 未所持も含めた全キャラを進化前後で見比べる |

**詳細はページに関係する段だけを出す**。全部並べると何を見ればいいか分からなく
なるため、`charDetailHTML(ch, extra, opts)` の `opts` で段を選ぶ。

一覧はどのページも同じ `.char-grid` を使い、入手順 / レア度 / オーラ / レベル /
開眼 / 所持数 で並べ替えられる。入手順に使う時刻は所持データの `at`
(**はじめて仲間にした時刻**。2体目以降では更新しないので並びが勝手に動かない)。

送還は数を指定して行う。**初期値は所持数と同じ**で、全部送還すると手持ちから
いなくなり、編成・貸し出しからも自動で外れる(確認ダイアログで名前を出す)。
「まとめて送還」で複数選択もでき、「被りだけ選ぶ」は各キャラ1体を残す数で選ぶ。

### ダンジョンの出撃は3段
ステージを選ぶと1つのモーダルの中で
**チーム選択 → サポート選択 → 4人そろった編成の確認 → 突入**
と進む。‹ で1段ずつ戻れる。スタミナを払うのは最後の「突入」の瞬間だけ。

突入した3人は `state.lastTeam` に残り、**ホームの1枚絵はこれを見せる**
(編成を触っただけでは変わらない)。未出撃のときは選択中のプリセットで代用する。

#### ホームでの見た目の大きさ(`scale`)
1枚絵は余白ごと枠に収める(`object-fit:contain`)ので、**絵の縦横比で
見た目の大きさが変わる**。枠は縦長(280x383)なので、横長の絵ほど小さく見える。
実測で、同じ枠に置いても縦に占める割合はキャラによって 48%〜86% とばらつく。

そろえるための倍率が `artStages[].scale`(段階ごと)と `artScale`(キャラ共通)。
`screens/home.js` の `artScaleOf()` が読み、`--art-scale` として
`transform:scale()` に流す。**段階ごとの指定が優先**される。
進化で構図が変わることがあるため(例: エミリは通常が縦長、進化後が横長で、
同じ倍率だと進化したとたん小さくなる)。

上げすぎると**頭がホームのバナーの裏に隠れる**。絵は切り取られないので、
枠からはみ出して上のバナーに潜り込む。横にも広がるので、
`280 x 倍率` が画面幅を超えると左右も切れる。**実際の画面で確かめること。**

管理ツールのキャラクター編集に「ホームでの大きさ」欄がある。
`build()` が `artStages` を組み直すので、**ここを拾い忘れると
開いて保存し直すだけで等倍に戻る**。`scripts/check-admin.cjs` が
その往復を見ている。

### オーラ
オーラは5色。🔥火 / 💧水 / 🌿木 / 💗癒 / 🌑闇。癒は攻撃ではなく**回復**を担当する。
盤面は7列×8行、同じオーラが**4つ以上**つながると消滅する。

**闇は後発のオーラで、第3章から盤面に加わる**(1〜2章は4色のまま)。
どの色が出るかはステージの `auras` が持ち、バトル開始時に `board.js` の
`setPalette()` へ渡している。盤面の生成と補充だけがこれを見るので、
スキルによる変換・生成は盤面に無い色でも作り出せる。
曜日ダンジョンは初級が4色、中級(ランク8)以上が5色。
ダンジョン選択画面のカードには、そのステージに出る色を丸で表示している。

### レアリティ・レベル・進化
- ガチャで出るのは **★1〜★4(N / R / SR / SSR)**。**★5(UR)は進化でのみ到達する**。
- キャラクターはレベルを持ち、ダンジョンクリアで編成キャラに経験値が入る。
  レベル上限はレアリティごと(★1:15 / ★2:20 / ★3:30 / ★4:40 / ★5:60)。
- **進化はキャラクターごとに1段階だけ**(★1→★2、★3→★4、★4→★5)。
  つまり **★5(UR)に到達できるのは★4のキャラクターだけ**で、レアリティの価値は保たれる。
- **進化**にはレベル上限到達 + 素材 + コインが必要。ダンジョンで
  オーラ別の結晶(紅蓮/蒼海/翠緑/聖光)と**進化の輝石**が手に入る。
- 進化するとステータスが伸びるだけでなく、**リーダースキルとスキルも強化**される
  (専用の強化版が無いキャラは `skills.js` の規則で自動的に強化される)。
- **レベルと進化でイラストが変わる**。`assets/chars/` に画像を置くと使われ、
  無い場合は絵文字で表示される(詳しくは `assets/chars/README.md`)。

### iOSでだけ描かれなかった敵のHPバー(未解明。回避の記録)

敵のHPバーが **iOS でだけ表示されなかった**。Chromium では再現せず、
原因の特定には至っていない。同じ形を作らないための記録を残す。

**分かっていること**(実機のスクリーンショットを画素で調べた結果)

- 名前と数字の間に**10px分の場所は確保されていた**。寸法は正しく、
  **枠も塗りも一度も描かれていなかった**(レイアウトではなく描画の問題)
- 同じ画面で、次のものは**描かれていた**
  - `.foe` の枠線、`.foe-badges`(ボタンの外の `div`)
  - ボタンの中の文字と敵のイラスト
  - ボタンの中の `.cg-corner`(`position:absolute`)
  - **ボタンの中の `.enemy-badge-art` / `.cg-img`(背景画像のスパン)**
- 描かれなかったのは、**flex ボタンの中にある、背景色で見せる薄い帯**
  (`.foe-health`)だけだった

**効かなかった直し方**

1. 中の塗りを `height:100%` の子要素から絶対配置へ
2. 子要素をやめ、`linear-gradient` の色の境目で残量を表す
   (`overflow` の切り抜きと、高さより大きい角丸も同時に外した)
3. `button` に `appearance:none`、バーに `position:relative`

**効いた直し方**

`<button>` の外(`.foe` 直下)へ移した。当たり判定は外側の `div` に
付け直したので、カードのどこを押しても狙いは変わる。

`.enemy-badge-art` のように「ボタンの中の背景画像」は描かれているので、
**「ボタンの中の背景はすべて駄目」ではない**。条件は絞り込めていない。
似た形(flex ボタンの中の、背景で見せる細い帯)は避け、迷ったら
ボタンの外に出すこと。`scripts/check-raids.cjs` が、HPバーがボタンの
外にあることと、カードのどこを押しても狙いが変わることを見ている。

**手元のチェックでは見つからない。** 実機で「出ない」と言われたら、
要素の大きさではなく**実際に塗られているか**をまず疑う。
スクリーンショットの画素を直接調べるのがいちばん早かった。

### 画像まわりの決めごと
- 画像はすべて **WebP**。PNG原本は `_original/` に置き `.gitignore` で除外する。
- ホームのメニューアイコンは **1枚のアトラス**(`assets/ui/menu_atlas.webp`、
  256px × 4列2行)にまとめ、CSSの `background-position` で切り出している。
  8枚を個別に置くとリクエストが8回になるため。並び順は style.css の
  `.t-*  .tile-icon` を参照。
- **キャラクターの丸アイコンも1枚のアトラス**(`assets/chars/char_atlas.webp`、
  128px × 8列)。一覧では数十枚を一度に並べるので、個別に読むとリクエストが
  その数だけ飛ぶ。描画は `ui.js` の `charIcon()`、格子の位置は
  `src/js/data/char-atlas.js`(生成物)。**イラストを足したら焼き直すこと**:

  ```sh
  python3 scripts/build-char-atlas.py   # アトラスと索引を作り直す
  ```

  アトラスに無いイラストは、これまで通り `<img>` + 絵文字フォールバックになる。
  立ち絵(`*_1.webp` など)はサイズが大きいのでアトラスに入れていない。
- 画面の背景は `#app::before` 1つで持ち回り、絵と暗幕だけを差し替えている。
  どの画面かは `nav.js` が `body[data-screen]` に入れる。
  - ホーム: `assets/ui/bg.webp`(常時)

  上から暗幕のグラデーションを重ねてUIの可読性を保っている。
- ダンジョンの背景(`assets/ui/danjon_bg.webp`)は画面全体ではなく
  **敵フィールド(`#enemyStage`)の中**に敷いている。敵がいる場所だけに出す。
- 敵は `assets/enemy/*.webp` のイラスト。読み込めないときは絵文字に落ちる
  (`gamedata.js` の `ENEMY_SPRITES` と `ENEMY_EMOJIS` が対になっている)。
- アプリアイコンは `any` と `maskable` を分けて用意している。maskable は中央80%の
  円が安全領域で、その外は切り落とされるため、装飾の金枠を除いて絵が端まで届く版を
  別途置いている(`icon-maskable-*.png`)。同じ画像を使い回すと枠が中途半端に切れる。

### 開眼
- **同じキャラクターを重ねて行う強化**。最大4段階で、段階ごとに別々の効果が付く。
  1段階につき手持ちの同キャラを**1体消費**する(消費するので手持ちが2体以上必要)。
- 効果の内容は `src/js/data/characters.js` の `AWAKEN_BY_ROLE`(ロール既定)と
  `AWAKEN_BY_ID`(キャラ個別)で決まる。操作時間延長 / スキルのCT短縮 /
  ATK・HP・RCVアップ の4種類。
- 反映は `resolveCharacter()` に集約している。ATK・HP・RCV とスキルCTはそこで
  適用し、操作時間だけはパーティ単位なので `battle/party.js` が合算する。
- **フレンドから借りたサポートキャラにも反映される。** 貸し出し情報として
  `rentalAwa` を `users/{uid}` に持たせ、クラウド保存のたびにレベルと合わせて
  最新へ同期している(貸し出し設定後に育てても古い値が残らない)。
- ガチャの被りはこの素材になる(それまで所持数は数えるだけで使い道が無かった)。

### キャラクターごとの攻撃
- 各キャラクターは固有のオーラを持つ。
- **自分のオーラを消したときだけ攻撃する**。消さなかったキャラは攻撃しない。
- 消した数が多いほど、そのキャラの攻撃力が上がる。
- 癒オーラのキャラは攻撃のかわりにパーティを回復する。
- 編成した4人がそれぞれ個別に敵を攻撃する(ダメージもキャラごとに表示)。

### 操作時間は10秒
最初にオーブへ触れてから**10秒**。指を離しても時間内なら何度でも掴み直せる。
時間が切れると自動的に手番が確定する。この10秒を**リーダースキルとスキルで
延ばして戦う**のが戦術の中心になる(上限40秒)。

### 全消しボーナスのチャンス盤面
盤面を空にすると、次の手番に**チャンス盤面**が配られる(`battle/chance.js`)。
1手戻すだけで5連鎖以上が走る「梯子」を仕込んだ盤面。

**盤面は隙間なく埋める。** 埋めていない時期があり、2つ困ったことになっていた。

- 5連鎖で打ち止め。梯子ぶんのオーラしか無いので、それ以上伸ばしようがない。
  埋めておけば、梯子に自分で組んだぶんを足せる(実測で6〜9連鎖まで伸びる)。
- **全消しループ。** 空きだらけの梯子は、消えると盤面がまた空になる。
  そのまま次の全消しボーナスを呼ぶので、延々と繰り返せてしまっていた。
  埋めたぶんが残るので、このループは起きない。

埋めると梯子が崩れて5連鎖に届かないことがある(埋めたオーラが落ちてきて、
別々の波が同時に消えて1波にまとまってしまう)。**実際に走らせて確かめ、
届かない埋め方は捨てている。** 平均1.3回、最大5回で通る。

埋める色は「置いた瞬間に消えない色」から選ぶので、梯子の塊(1波目)以外の
塊はできない。配られた時点で勝手に消えることはない。

### チャンス盤面の光(入れ替える2マス)
盤面を埋めたぶん、梯子は絵に紛れて見つけにくい。そこで**入れ替える2マスを
金色に光らせる**(`renderer.js` の `drawSwapHint`)。`createChanceBoard` が
返す `swap` を `run.chanceHint` に覚えておくだけ。

**光はオーラの後ろに描く。** 上から重ねると光の膜でオーラの色がにごり、
「どの色を動かすのか」が読めなくなる。マスはオーラより一回り大きいので、
後ろに描いても縁はきちんと見える。

**オーラを掴んだ時点で消す**(`onPointerDown` で `chanceHint` を捨てる)。
役目は「見つける」ところまで。点けたままだと動かしているオーラの色が
読みにくくなる。中断データにも載せてあるので、閉じて開き直しても
まだ掴んでいなければ光は残る。

光の座標は保存データから来ることがあるので、`drawSwapHint` は
**形が壊れていても描かずに済ませる**。ここで落ちると毎フレーム落ちて
操作不能になる。

なお、梯子は盤面に紛れるが**「唯一の正解手」ではない**。
5連鎖に届く1手は平均して3手ほどある(消滅連結数3のときは5手ほど)。
光はあくまで確実な1手を示すだけで、自分で別の手を組んでもよい。

### リーダースキル
発動するのは**自陣リーダー(編成1人目)**と**サポート**の2つ。
効果は `src/js/data/skills.js` に定義していて、次の種類がある。

| 効果 | 例 |
| --- | --- |
| オーラ別の攻撃倍率 | 業火の覇者「火オーラ2.2倍・操作時間+2.0秒」 |
| 全オーラの攻撃倍率 | 大聖女の福音「全オーラ1.4倍・回復2.0倍・操作時間+2.0秒」 |
| 操作時間の延長 | 氷結の思考「オーラ操作時間+3.0秒」 |
| 最大HP / 回復力 | 聖騎士の盾「最大HP1.5倍・被ダメージ15%減」 |
| コンボ条件 | 風読みの極意「5コンボ目以降の攻撃力1.8倍」 |
| 連結条件の緩和 | 世界樹の恵み「連結3個で消えるようになる」 |

### スキル
バトル中に仲間をタップして発動。ターン経過でチャージされる(CT)。
操作時間の延長、回復、固定ダメージ、オーラ変換、盤面シャッフル、
攻撃力アップ、被ダメージ軽減、敵の攻撃遅延などがある。

### ガチャ
- **オーブ召喚**(最高 SSR / ピックアップ開催)と**フレポ召喚**(N〜SR中心)の2種類。
- 単発と**10連**があり、10連は1回ぶんお得＆**★3以上が1体確定**。
- オーブ召喚の★4は12%。そのうち `PICKUP_RATE`(現在30%)がピックアップ枠で、
  残りを**ピックアップを除く**★4で均等に分ける(1体あたり約0.76%)。
  ピックアップを通常枠にも残すと表示より出やすくなるため除外している。
- 召喚演出は「魔法陣 → オーラのオーブが集まる → 溜め → フラッシュ → カード出現」。
  集まるオーブの色が期待度を示す(青=通常 / 金=SR以上 / 虹=SSR確定)。画面タップでスキップできる。

### ダンジョン / スタミナ / ランク
- ダンジョンは**ノーマル / テクニカル / 降臨 / 曜日**。ホームの
  ダンジョンから、この並びで選ぶ。
- **ノーマルは全10章 × 5ステージ(計50)**。ステージIDは通し番号で、
  章の最終ステージをノーマルでクリアすると次の章が解禁される。
  奥へ進むほど結晶のドロップ量・コイン・キャラ経験値が増える。
- **テクニカルは全10階層 × 5ステージ(計50)**。ID は 3001〜3050
  (通常の1〜50、曜日の1000番台、降臨の2001とぶつからない番号)。
  解禁の仕方と難易度(ノーマル/ハード)はノーマルダンジョンと同じ。

#### テクニカルダンジョン
**ボスはいない代わりに、250フロアすべてが特殊行動を持つ**。オーラを
消すだけでは通らず、連鎖数・形・色を組み立てて崩す場所。特殊行動は
10種類を順に巡らせる(1ステージ5フロアで5種類、2ステージで一巡)。

| 続き方 | 種類 |
| --- | --- |
| フロアの間ずっと(`passives`) | コンボガード / 根性 / ビルドアップ |
| ターン数を区切って先制(`preemptive`) | 形ガード / オーラ吸収 / バインド / スキル遅延 / 操作時間減 / 操作時間固定 / オーラバインド |

形ガードとオーラ吸収をフロアの間ずっと続けると、手持ちのオーラ次第で
手も足も出なくなるので、**この2つは必ずターン数を区切っている**。
ずっと続けるのは、耐えきれる3種類だけ。

**形ガードはオーラを問わない。** 形さえ合っていればどの色で作っても通る。
色と形の両方を指定すると、その色が盤面に足りないだけで詰むため。
効いているあいだは、敵の前に必要な形を `.foe-shield` としてうっすら重ねる
(`battle/enemy-shield.js`)。形はバッジを押さないと読めないので、
盤面を見ながら確かめられるようにしてある。
判定と表示で形がずれると直しようのない理不尽になるので、
**形の定義は `battle/enemy-skills.js` の `SHAPES` 1か所だけ**に置き、
判定・演出・シールドの3つがそこを参照している。

**初クリア報酬**はダイヤ1個。`stage.firstClearOrb` を持つステージで、
**難易度ごとに1回だけ**配る(周回では出ない)。判定は `finishRun()` で
`state.progress` に印を付ける**前**に行う。まだ取っていないぶんは
ステージカードに「初💎1」と出る。
- **曜日ダンジョン**は日替わりで手に入るものが変わる。初級/中級/上級の
  3段階があり、プレイヤーランクで解放される。

  | 曜日 | 内容 |
  | --- | --- |
  | 月 | 🩷 聖光の結晶(回復キャラの進化素材) |
  | 火 | 🔴 紅蓮の結晶 |
  | 水 | 🔵 蒼海の結晶 |
  | 木 | 🟢 翠緑の結晶 |
  | 金 | 💰 ゴールド特化(素材は落ちない) |
  | 土 | 🟣 常闇の結晶 |
  | 日 | 📗 キャラクター経験値アイテム |

  常闇だけ長らく曜日が無く、通常ダンジョンでも**50ステージ中8つ**
  (3章以降の各章5ステージ目)しか落とさない詰まりどころだった。
  土日が両方とも経験値で重複していたので、土曜を常闇に充てて埋めている。
  `tests/economy.test.mjs` が「キャラが存在するオーラの結晶は、どれかの
  曜日で必ず取れる」ことを見張っている。

- 1ステージ5フロア。フロアは**自動で進み**、フロア間の回復はない。
- 敵は一定ターンごとに攻撃してくる(ボスは毎ターン)。
- クリアすると進化素材がドロップする。ステージごとに主に落ちる結晶のオーラが違う。
- スタミナは3分で1回復。初期ダンジョンの消費は5。
- ステージクリアで EXP を獲得。**ランクアップ時は「現在のスタミナ +
  ランクアップ後の最大スタミナ」になる**ので、スタミナは最大値を超えて
  オーバーフローする(超過ぶんは自然回復では減らない)。

### ショップ / 経済

ショップは**コイン建て**と**ダイヤ建て**が混ざる。`SHOP_ITEMS` の
`currency: 'orb'` が付いたものだけダイヤ建てで、付いていなければコイン建て。
`dailyLimit` を付けると**1日に買える本数**を絞れる。買った本数は
`state.shopLog`(`{ date, counts }`)に日付ごとに記録し、日付が変われば
`shopRemainingToday()` が自動で戻す。クラウド保存にも載せているので、
端末を変えても上限をすり抜けられない。

| 品物 | 値段 | 備考 |
| --- | --- | --- |
| キャラクター4種 | 800 / 2200 コイン | **買い切り(1回きり)** |
| 💠 進化の輝石 ×2 | 4,000 コイン | 1日1個まで |
| 今日の結晶 ×5 | 2,500 コイン | 1日1個まで(金・日は並ばない) |
| 📗 経験の書 ×3 | 3,000 コイン | 1日1個まで |
| 👁️ 開眼の証 ×1 | 12,000 コイン | 1日1個まで |
| オーブ小袋 💎3 | 20,000 コイン | **1日1個まで** |
| スタミナドリンク ⚡50 | **💎2** | 1日3本まで |

素材枠は**コインの行き先を毎日作る**ためのもの。全部買うと1日21,500
コイン、小袋と合わせて41,500コインなので、回し込む人の1日の収入
(平日の最良で約58,000コイン)でも「今日はどれを取るか」が起きる。

「今日の結晶」(`type: 'crystalToday'`)は**その日の曜日ダンジョンと同じ
結晶**を売る。スタミナを使わずに買い足せる枠なので、結晶の落ちない
金曜(ゴールド)と日曜(経験値)には並べない(`inStock()` で外す)。

#### スタミナドリンクの値段の決め方

実装前に測った数字:

| 測ったもの | 値 |
| --- | --- |
| スタミナの自然回復 | 3分で1 = **1日480** |
| スタミナ上限 | 100 + ランク×5 |
| コイン効率(1-1) | 30 コイン/スタミナ |
| コイン効率(10-5 ノーマル) | 113 コイン/スタミナ |
| コイン効率(**平日の最良 = 9-2 ハード**) | **121 コイン/スタミナ** |
| コイン効率(**金曜「黄金の坑道 上級」**) | **600 コイン/スタミナ** |
| オーブ小袋 | 1ダイヤ = 1667 コイン |
| ガチャ | 単発5ダイヤ / 10連45ダイヤ |
| ダイヤの入手 | 章の最終ステージ約20 + テクニカル初クリア100 + ログボ月12前後 |

曜日ダンジョンに**ハードはない**(`stage.daily` なら `hard` は常に false)ので、
600コイン/スタミナがコイン効率の上限になる。これと小袋を繋ぐと
**スタミナ1 = 0.36ダイヤ**。

- **コイン建てにはできない。** 600コインより安くコインでスタミナを買えたら、
  スタミナ→コイン→スタミナがそのまま無限に回る。
- **ダイヤ建てでも輪は閉じない。** 小袋がある限り
  「ダイヤ→スタミナ→コイン→ダイヤ」は繋がっていて、💎2の50スタミナは
  金曜上級なら30000コイン = **18ダイヤ**ぶんになる。
  塞ごうとすると💎18以上になり、ガチャ1回5ダイヤに対して誰も買わない。
- なのでドリンク側では**増える量を頭打ちにする**方針を取り、
  **1日3本(+150スタミナ、自然回復480の約3割)**で止めている。

#### ショップのキャラが買い切りな理由

初心者向けの拾い物枠であって、素材の自動販売機ではない。
何度も買えると「買って送還」で素材とコインが増え続けてしまう。

| | 購入 | 送還で戻る | 実質 |
| --- | --- | --- | --- |
| ゴラン ★2 | 800 | 500コイン + 🔴2 + 👁️1 | **300コインで結晶2個と開眼の証1個** |
| レイナ等 ★3 | 2,200 | 1,500コイン + 結晶5 + 👁️1 | **700コインで結晶5個と開眼の証1個** |

結晶1個あたり140〜150コインで無制限に買えていた。**送還すると所持数は
0に戻る**ので、所持の有無では止められない。`state.shopTotal` に通算購入数を
持たせ、`totalLimit` で止めている(日付では戻らない。クラウド保存にも載せて
あるので端末を変えても復活しない)。

この上限があるぶん、素材をショップに並べるときの値段も自由に決められる。

#### オーブ小袋に1日1個の上限がある理由

小袋は**コインをダイヤに替える唯一の道**なので、ここが開いていると
ダイヤの供給がコイン収入にそのまま比例してしまう。上限が無かった頃の
理論上の上限は**週437ダイヤ(1日平均62、10連87回ぶん)**だった。

| | スタミナ | コイン | 全体比 |
| --- | --- | --- | --- |
| 金曜(上限まで貯めて回す) | 670 | 402,000 | 55% |
| 平日6日(9-2ハード 121コイン/スタミナ) | 2,690 | 326,124 | 45% |
| 週合計 | 3,360 | **728,124** → 旧レートで**437ダイヤ** | |

意図した供給が「初クリア約120(1回きり) + ログボ月12前後」なので桁が違う。

**原因は金曜ではなく小袋のレートそのものだった**。曜日ダンジョンは週1日
しか開かない(`renderDailyList()` はその日のぶんしか出さない)ため金曜は
全体の55%でしかなく、**金曜を丸ごと消しても週244ダイヤ(1日35)残る**。
1667コイン/ダイヤという値が、金曜に限らず**すべての**コイン収入に対して
安すぎたということ。

なので**値上げではなく上限**で止めている。値上げだとダンジョンを足すたびに
レートを取り合うことになり、同じ穴が開き直す(実際テクニカルのコイン量が
もう少し高ければ今回また開いていた)。上限なら**コイン収入がいくつでも
蛇口が 3ダイヤ/日 で止まる**ので、この先バランスを触っても安全。

値段の20,000は★4→★5の進化1回ぶんと同額にしてある。「進化を1段進めるか、
ダイヤ3個を取るか」という読める取引にしたいため。

この上限のおかげで**ダイヤ→スタミナ→コイン→ダイヤの輪も赤字で閉じる**。
ドリンクを3本買っても💎6払って戻るのは最大💎3なので、回すほど損をする。
`check-shop.cjs` がこの不等式(`小袋の1日ぶん < ドリンクの1日ぶん`)を
見張っているので、どちらかの値をいじって輪が黒字になると落ちる。


## 開発

ES Modules を使うため `file://` では動かない。ローカルでは HTTP で配信する。

```sh
python3 -m http.server 8000
# → http://localhost:8000/index.html
```

セーブデータは `localStorage` の `acb_state` キー(現行 `version: 9`)。
旧フォーマットは起動時に自動で移行される。
- v4以前(5属性 / モンスター編成): 同じオーラ・レアリティの人物キャラクターへ読み替え、
  旧 光/闇 は癒(ピンク)へ集約される。
- v5(所持数のみ): `{n, star, lv, xp}` 形式へ変換される。
- v8以前(編成が1つだけ): `team` を `teams[0]` へ移し、残り4つは空のプリセットにする。
  所持データには入手時刻 `at` が加わる(移行分は 0 = いちばん古い扱い)。

### アプリの版(起動できなくなるのを防ぐ)

サービスワーカーはHTMLとJSを**別々に**取りに行くので、通信が不安定だと
「古い index.html + 新しいJS」で起動してしまうことがある。その状態では
`main.js` が無い要素を触って落ち、**ローディングが0%のまま固まる**。
利用者からは原因が分からず、手の打ちようもない。

これを防ぐため、版を3か所にそろえて突き合わせている。**変えるときは必ず3つとも**:

| 場所 | 例 |
|---|---|
| `index.html` の `<meta name="app-version">` | `55` |
| `src/js/core/version.js` の `APP_VERSION` | `'55'` |
| `sw.js` の `CACHE_NAME` | `aura-connect-v55` |

いま動いている版は**マイページの「バージョン」**で確認できる。
不具合の切り分けでは、まずここが最新かを見ること。

食い違いを見つけると `main.js` がキャッシュとサービスワーカーを捨てて
読み込み直す(`core/recovery.js` の `resetApp()`)。読み直しても直らないときは
**必ず画面に出す**(`showBootError()`)。どちらも**セーブデータには触らない**。

さらに保険として、`index.html` の先頭に見張り番を直接書いてある。
15秒たってもタイトルが出なければ同じ復旧画面を出すので、
モジュールが1行も動かない場合でも「読み込み直す」を押せる。

### 画面遷移と戻る操作

どの画面もホームのメニューから1段だけ潜る構成なので、履歴スタックは持たない。
トップバーの ‹ は `goBack()` で、画面内に階層があるとき
(ダンジョンの種別選択など。`registerBackHandler()` で登録する)はそこへ、
無ければホームへ戻る。

Android の端末側の戻るは `popstate` で拾う(`nav.js` の端末の戻る操作)。
履歴に身代わりを1つだけ積んでおき、戻るたびに消費 → 処理して積み直す。
手前に出ているものから順に、

1. モーダルが開いていれば閉じる(`data-back-close` を付けたボタンを押す)
2. バトル中は設定(リタイア)を開く。進行中のランを不意に捨てないため
3. ホーム以外なら `goBack()`
4. ホームなら、続けてもう一度でアプリを閉じる(1回目はトーストで知らせる)

モーダルを足したら、閉じる/キャンセルのボタンに `data-back-close` を付ける。

## 管理ツール (admin/)

ゲーム本体とは別の PWA。`admin/index.html` を開くと使える。
モンスター・降臨ダンジョン・キャラクターを編集し、GitHub へ直接 push する。

### 仕組み

編集した内容はすぐには送らず、**端末の中の「下書き」に溜める**
(`admin/js/draft.js` → localStorage)。リリース画面でまとめて確認してから
**1コミットで push** する。途中で失敗しても中途半端な状態が残らないよう、
GitHub の Git Data API (blob → tree → commit → ref) を使っている。

書き出し先は `src/js/data/custom.js` の1ファイルだけ。
これは**機械生成なので手で編集しない**。

下書きは push のたびに空になるので、書き出しは
**いまの custom.js に下書きを重ねる**形にしている(id / key が同じものは
下書きが勝ち、無いものはそのまま残る)。重ねずに書くと、キャラを足した次の
push でそのキャラが消える。`tests/admin-release.test.mjs` が見張っている。中身は JSON リテラルだけで処理は
書かない方針にしてあり、`tests/admin-release.test.mjs` が
「本当に import できる JS になるか」を毎回確かめている
(引用符・山括弧・改行が名前や台詞に入っても壊れないこと)。

```
admin/js/custom-source.js   ← ここが吐いた文字列がそのままソースになる
        ↓ push
src/js/data/custom.js       ← 機械生成。手で触らない
        ↓ import
data/enemy-master.js / raids.js / characters.js で本体と合流
```

### 画面

| タブ | できること |
| --- | --- |
| ホーム | いまの中身の要約と下書きの状態 |
| モンスター | アイコン一覧 → タップで編集。ステータス・行動パターン・**変身(forms)** |
| 降臨 | フロアごとの配置。マスターの基礎値に**倍率**をかける |
| キャラ | 一覧 → 詳細。新規はロール選択でステータスを自動生成 |
| ガチャ | ピックアップの差し替え・バナー・**アイコンのアトラス焼き直し** |
| スキル | 一覧と検索。**既存を分解して組み替え、新スキルを作る** |
| プレゼント | 配布期間と中身を決めて、プレゼントボックスへ配る |
| 点検 | 整合性チェック・ガチャ排出率・コイン効率・経済の安全弁 |
| リリース | 版を+1して push |

### スキルをパーツから作る

**まったく新しい「効果の種類」は管理ツールでは作れない。** 新しい効き方を
足すには `battle/` 側の実装が要るため。できるのは:

1. 既存スキルを**分解**して、どのパーツでできているかを見る
2. パーツを足し引きし、倍率やターン数を変える
3. 名前を付けて別のスキルとして登録する

実際のスキルはほぼ全部この組み合わせでできているので、これで大半は作れる。

パーツ表は `admin/js/skill-parts.js`。**ここに並ぶのはエンジンが実際に読む
キーだけ**で、`tests/skill-parts.test.mjs` が `battle/` のソースを読んで
それを毎回確かめている(飾りのパーツを足しても効果が出ないため)。
分解と組み立てが往復で一致することも、既存スキル全部に対して見ている。

| | パーツ |
| --- | --- |
| リーダースキル | オーラ別/全体の攻撃倍率、コンボ数での倍率、最大HP、回復力、操作時間、被ダメ軽減、必要連結数 |
| スキル | 操作時間+、HP回復、固定ダメージ、オーラ変換、オーラ生成、シャッフル、攻撃力アップ、被ダメ軽減、敵の攻撃遅延 |

説明文は空にしておくと**パーツから自動で書く**(`describeLeaderSkill` /
`describeActiveSkill`)。手で書くと以後そのままになるので、
中身と食い違っていることを画面で知らせる。

既存と同じIDにすると**そのスキルを上書き**する。倍率だけ直したいときに使う。
作ったスキルは、同じ下書きの中でそのまま新キャラに付けられる。
★5進化時の自動強化(`evolvedLeaderSkill` / `evolvedActiveSkill`)も
そのまま効く。

### 敵の行動は「攻撃」と「特殊行動」を兼ねられる

`enemySkills.actions` の1つは `{ attack, effects, dialogue }` で、
**攻撃しながら効果も撃てる**(キュウコの進化後が元からこの形)。
管理ツールの「行動を足す」でも、攻撃のチェックと特殊行動を両方入れられる。

### 敵フィールドの中央寄せ

**iOS の `<button>` は flex コンテナにしても `align-items` が `stretch` にならない。**
中の要素が中身の幅まで縮んで cross-start(左端)に置かれるため、
`.foe-target` の中にある敵の絵と名前がまとめて左へ寄る。
Chromium では既定が stretch なので、この環境では再現しない。

```css
button{ ... align-items:stretch; }
```

flex でないボタンは `align-items` を無視するので、基本スタイルでまとめて指定している。

`text-align:center` では直らない。箱が中身の幅に張り付いてしまうと、
その中での文字揃えをいくら指定しても位置は変わらないため。
最初これで直そうとして効かなかった。

一度 `#enemyRoster` 側を疑って端の `.foe` に auto マージンを入れたが、
**あれは誤診だった**。実機のスクリーンショットを実測したところ、
`.foe` の枠(HPバーの幅)は画面の中央に来ていて、ずれていたのは枠の中身だけだった。
マージンは保険として残してある(正しいブラウザでは `justify-content:center` と同じ結果になる)。

```css
#enemyRoster > .foe:first-child { margin-left:auto; }
#enemyRoster > .foe:last-child  { margin-right:auto; }
```

検査は **枠(`.foe`)を基準に測ること**。絵が「`.foe-art` の中で中央か」だけを見ていると、
箱ごと縮んだこの不具合をすり抜ける(実際にすり抜けた)。
`scripts/check-raids.cjs` で箱が枠いっぱいに伸びているかを、
`scripts/check-technical.cjs` で絵が枠の中央に来ているかを見ている。

### 敵の特殊行動の演出

`battle/enemy-motion.js` が短命のキャンバスに描く。**先制でも演出は出す**。
「敵の行動！」の帯(750ms)だけは先制では省く(ほぼ毎フロア来るのでテンポが悪い)。
以前は先制だと演出ごと飛ばしていたため、**バインドや操作時間短縮は
一度も見えていなかった**。何をされたか分からないまま操作時間だけ削られるのが
一番つらいので、演出は残す。

- **バインド** … 紫のモヤが敵から対象へ飛び、着いた相手を鎖と「封」で包む
- **操作時間短縮** … 盤面いっぱいの時計を魔法陣のように重ね、針が反時計回りに
  巻き戻る。巻き戻した角度を扇で残すので、どちら回りかが一目で分かる
- **操作時間固定** … 同じ時計だが針は12時で止まり、外に四角い枠が出る

### 待たずに手番を終わらせる「発火」

操作時間が余ると、切れるまで待たされてつらい。操作中だけ盤面の右上に
`#fireNowBtn` を出し、押すと時間切れと同じ経路(`endTurnNow()`)で手番を解決する。

盤面の**外(真上)に浮かせている**。流れに入れると盤面が下がり、セルの大きさが
変わって画面が揺れてしまうため。`z-index` は `#playerEffects`(8)より上にする。
下に潜ると、見えているのに押せないボタンになる。

### ホームのバナー

ホームの宣伝バナーは `src/js/data/banners.js` が決め、**数秒ごとに入れ替わる**
(`BANNER_INTERVAL`)。並ぶのは2種類:

- **降臨** … `RAID_STAGES` の**いちばん新しいもの1枚だけ**。
  新しい降臨を足すと、それまで出ていたバナーと自動で入れ替わる。
  画像は降臨データの `banner`。
- **ガチャ** … `CUSTOM_SETTINGS.gachaBanner`。ピックアップがいるときだけ出す。

画像の無いものは並べない。1枚しか無ければ切り替えも点も出さない。

送りの△は**バナーの外(左右)**に置く。絵の上に重ねるとバナー自体が
見えにくく、飛び先を押すつもりで送ってしまう。
右のプレゼント箱(52px)を避けるため、`.home-banner` は
`max-width:calc(100% - 58px)` で止めてある。

実装で気をつけている点が2つある。

1. **要素は作り直さず `on` クラスの付け替えだけで見せ替える**。
   作り直すとCSSトランジションが効かず、その場で切り替わってしまう。
2. **出ていないバナーは `pointer-events:none` で当たり判定ごと外す**。
   `opacity:0` は透明になるだけで指は吸うので、
   重なった裏のバナーの飛び先へ飛ばされてしまう。

### ガチャのピックアップ

`CUSTOM_SETTINGS` で差し替えられる(管理ツールのガチャタブ)。

| キー | 意味 |
| --- | --- |
| `pickupId` | ピックアップにするキャラID |
| `pickupRate` | ★4帯のうちPUが占める割合(既定 0.3) |
| `pickupOff` | `true` でピックアップを開催しない |

指定が無ければ従来どおり `featured: true` のキャラと 0.3。

**「開催しない」を空文字で表さないこと。** 空文字は「未設定」と区別が付かず、
既定の featured キャラへ黙って戻ってしまう。そのために `pickupOff` を
分けてある。

差し替えは**ガチャ画面の表示と抽選の両方**に効く。開催しないときは
PU枠を `hidden` にし、「ピックアップ開催中」の文言も出さない
(空の枠が残ると開催中に見えるため)。
`scripts/check-gacha-pu.cjs` が3つの状態を本物の画面で確かめている。

### アイコンのアトラス

`python3 scripts/build-char-atlas.py` のほかに、**管理ツールからも焼ける**
(`admin/js/atlas.js`。canvas で同じ結果を作る)。Python を回せない端末から
キャラを足したいときのため。

焼き直しは**必須ではない**。アトラスに無いアイコンは `core/ui.js` の
`charIcon()` が `<img>` へフォールバックするので、足しただけでも表示される。
一覧のリクエストを1回にまとめたいときだけ流せばよい。

出力は `assets/chars/char_atlas.webp` と `src/js/data/char-atlas.js` の2つ。
`tests/admin-release.test.mjs` が、ツールの書き出す索引が
build-char-atlas.py のものと同じ形になることを確かめている。

**アトラスは起動中に裏で取りに行く**(`core/boot.js` の `WARM_IMAGES`)。
素材のなかで一番大きく(1024x768・約540KB)、キャラ一覧・ガチャ・
サポート選択と、ほぼ全部の画面で使うため。

以前はここに無く、**画面を開くまでリクエストすらされていなかった**。
サポート選択を開いて測ると、アトラスの取得が始まるのは画面を開いたあと。
そのあいだアイコンだけが空白のまま残り、スクロールしても出てこない、
という見え方になっていた(取得後にまとめて出る)。

`BASE_IMAGES` には入れないこと。あちらは読み終わるまでローディングを
進めない一覧なので、540KB ぶん起動が丸ごと長くなる。
`WARM_IMAGES` は起動が終わってから投げるだけなので、
タイトルを見ているあいだに取れている(実測でタイトル到達は変わらず、
サポート画面を開く前には揃っていた)。
`scripts/check-character.cjs` が、起動中にリクエストが出ていることを見ている。

### アクセストークン

GitHub の **Fine-grained personal access token** を使う。
権限はこのリポジトリの **Contents: Read and write** だけで足りる。

⚠️ トークンは**その端末の localStorage** に入る。つまり
**端末を触れる人には読める**。共用端末では使わないこと。
リポジトリには入らない(`admin/js/github.js` が localStorage としか
やりとりしない)。消すときは ⚙ → 「トークンを消す」。

### 版上げ

`index.html` / `src/js/core/version.js` / `sw.js` の3か所は、
ずれるとゲームが起動しなくなる(→ 「アプリの版」の節)。
リリース画面は3か所を読んで**必ず一緒に +1** する。
数字として読めなかったときは 0 扱いにせず止める
(読み取り失敗で版が1に巻き戻ると、版ずれループに入るため)。

### 画像

PNG/JPEG を選ぶとツール内で webp にしてから push する
(`admin/js/image.js`、`canvas.toBlob('image/webp')`)。
1枚絵は長辺1024px、アイコンは中央で正方形に切って128px角、
バナーは1080×400(ホームのバナー枠と同じ 2.7:1。ここがずれると
上下を切られる)。

⚠️ **画像はメモリにしか置いていない**(localStorage に Blob は入らない)。
選んだセッションのうちに push すること。再読み込みすると画像だけ外れる。
リリース画面がその旨を出す。

新しいキャラのアイコンは**アトラスに焼かなくても動く**。
`core/ui.js` の `charIcon()` がアトラスに無いものは `<img>` へ
フォールバックするため。まとめて焼き直したくなったら
`python3 scripts/build-char-atlas.py` を流す。


## フレンド機能 / クラウド保存(Firebase)

Firebase は**設定済みのときだけ**動的 import で読み込むため、未設定でも
オフラインでもゲーム本体(ローカル保存)はそのまま遊べる。

`src/js/core/firebase.js` の `firebaseConfig` を、ご自身の Firebase プロジェクトの
設定値に置き換えると有効になる。

**すべて無料枠(Spark プラン)の範囲で動く構成にしている。** Cloud Functions は
Blaze プラン(従量課金)が必須なので使っていない。したがってサーバーサイドでの
検証は行えず、防御は Firestore のセキュリティルールだけが担っている。

### フレンド登録は黙って失敗させない

「登録したのに居ない」「消えた」という声のほとんどは、**登録そのものが
失敗していて、それが画面に出ていない**ことによる。以前は
`addFriendByCode()` が例外を拾っておらず、通信が切れていると

- 例外がそのまま画面側の `await` まで抜ける
- トーストも出ないので、押しても何も起きないように見える

という形になっていた。いまは3段構えにしてある。

1. **理由を返す。** クラウド側の失敗は `cloudErrorMessage()` で
   「通信できていないようです」等の日本語に直して返す。画面側にも
   try/catch を置き、そこを抜けた例外でも必ず何か出す。
2. **自分の一覧への書き込みだけが成否を決める。** 相手の一覧へ書けなかった
   ときは `linkPending` の印を自分の書類に残し、成功として扱う。
   ここで丸ごと失敗にすると、相手側が一時的に書けなかっただけで
   「登録したのに居ない」になってしまう。印は次の一覧更新でやり直す。
3. **クラウドが0件でも手元の一覧を消さない。** 削除しても `removed` の印が
   残る作りなので、本当に0件になることはない。0件で返るのは別の uid を
   見ているとき(匿名ログインが作り直されたなど)で、そのまま上書きすると
   フレンドが全員消える。

`scripts/check-friends.cjs` が、メモリ上の偽 Firebase に失敗を注入して
この3つを確かめている(本番のプロジェクトには触らない)。

なお**サポート選択のフレンドタブに出るのは、貸し出しキャラを設定している
フレンドだけ**(`fetchFriendRentals()`)。フレンド一覧には居るのに
サポートに出てこないのは、これで正しい。

### セットアップ手順

1. Firebase コンソールでプロジェクトを作成
2. Authentication → Sign-in method で **「匿名」と「メール/パスワード」の両方**を有効化
3. Firestore Database を作成
   - **本番環境モード**で開始する(テストモードは30日間だれでも全データを読み書きできる)
   - ロケーションは後から変更できない。国内向けなら `asia-northeast1`(東京)
4. Firestore → ルール に下記を貼り付けて公開
5. `firebaseConfig` にプロジェクトの設定値(apiKey 等)を貼り付け

apiKey はクライアントに埋め込む前提の識別子なので、公開リポジトリに入っていても
問題ない。ただし裏を返すと**実際の防御はセキュリティルールだけ**になるため、
公開前に Google Cloud Console でのAPIキー制限(HTTPリファラー)と App Check の
設定を検討すること。

### セキュリティルール

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    function signedIn() { return request.auth != null; }
    function isMe(uid)  { return signedIn() && request.auth.uid == uid; }
    function onlyChanged(keys) {
      return request.resource.data.diff(resource.data).affectedKeys().hasOnly(keys);
    }
    // 他人が加算できるのは、あいさつの固定額と貸し出し使用回数(+1)だけ
    function isGreetReward() {
      return onlyChanged(['pendingFrepo'])
        && request.resource.data.pendingFrepo is int
        && request.resource.data.pendingFrepo == resource.data.pendingFrepo + 10;
    }
    function isRentalUse() {
      return onlyChanged(['rentalUseCount'])
        && request.resource.data.rentalUseCount is int
        && request.resource.data.rentalUseCount == resource.data.rentalUseCount + 1;
    }

    match /users/{uid} {
      // 名前・アイコン・貸し出しキャラはフレンドが読む必要がある
      allow read:   if signedIn();
      allow create: if isMe(uid);
      allow update: if isMe(uid) || (signedIn() && (isGreetReward() || isRentalUse()));
      allow delete: if false;

      match /friends/{friendUid} {
        allow read:  if isMe(uid);
        // 自分の一覧は自由に。他人は「自分自身を相手の一覧に追加する」ことだけできる
        allow write: if isMe(uid) || (signedIn() && friendUid == request.auth.uid);
      }

      match /save/{doc} {
        allow read, write: if isMe(uid);   // セーブデータ本体は本人のみ
      }
    }

    match /friendCodes/{code} {
      allow read:   if signedIn();
      allow create: if signedIn() && request.resource.data.uid == request.auth.uid;
      allow update, delete: if false;      // 一度発行したコードの奪取を防ぐ
    }

    // 運営からのプレゼント。全員が読むだけで、書き込みはコンソールからのみ
    match /gifts/{giftId} {
      allow read:  if signedIn();
      allow write: if false;
    }
  }
}
```

このルールで防げるのは「他人のセーブデータの読み書き」「他人のプロフィール改竄」
「フレンドコードの乗っ取り」「任意額のフレポ付与」「使用回数の一括水増し」。

一方、Cloud Functions を使わない以上、**次の2つは防ぎきれない**。
- 自分のセーブデータの改竄(クライアントが書く値をそのまま保存しているため)
- フレンド報酬の連打による稼ぎ(1回あたりの額は固定できるが、回数を制限できない)

いずれも同期型の対人要素が無い現状では実害が小さいため、無料枠を優先して許容している。
ランキング等を入れる場合はここが前提から崩れるので、設計を見直すこと。

### 運営からのプレゼント(gifts コレクション)

Cloud Functions が使えないので、配布は「全員が読めるドキュメントを置き、
受け取り済みかどうかは端末側(`giftLog`、クラウドのセーブにも乗る)で管理する」
方式にしている。Firebase コンソールで `gifts` コレクションにドキュメントを
1つ作れば、次の起動時に全プレイヤーのプレゼントボックスへ入る。

| フィールド | 例 | 備考 |
| --- | --- | --- |
| `title` | `リリース記念プレゼント` | 見出し |
| `note` | `遊んでくれてありがとう!` | 省略可 |
| `coin` / `orb` / `frepo` / `stamina` | `1000` / `5` | 数値。要らないものは省略可 |
| `char` | `dk_shion` | キャラクターID。受け取るとそのまま所持に加わる |
| `from` / `to` | `2026-09-13` | 配布期間(省略可)。期間外は配らない |

ドキュメントIDが受け取り済み判定のキーなので、**配布後に内容を書き換えても
すでに受け取った人には届かない**。配り直したいときは新しいIDで作ること。
起動ごとに最大20件を読むため、古いものはコンソールから削除しておく。

### 管理ツールから配る(CUSTOM_GIFTS)

管理ツールの「プレゼント」タブで作ると `custom.js` の `CUSTOM_GIFTS` に入り、
次の起動でプレゼントボックスへ届く。Firestore を使わないので、
配るのに通信の設定は要らない(受け取りもオフラインでできる)。

| 欄 | 意味 |
| --- | --- |
| `key` | 配布の目印。端末はこれを覚えていて、同じ key は二度と配らない |
| `title` / `note` | 見出しとひとこと |
| `from` / `to` | 配布期間(YYYY-MM-DD)。省略すると期間なし |
| `coin` / `orb` / `frepo` / `stamina` | 数量 |
| `char` | キャラクターID。受け取るとそのまま所持に加わる |

**中身を書き換えても、受け取り済みの人には届かない。** 配り直すときは
新しい key で作る。期間前のものは配らずに見送る(先に配ってしまうと、
期間に入っても「配布済み」の扱いで届かなくなるため)。

### コードに埋め込む配布(BUILTIN_GIFTS)

Firestore を使わずに全員へ配りたいものは `gamedata.js` の `BUILTIN_GIFTS` に
書く。オフラインでも初回起動時に必ずプレゼントボックスへ入る。配布済みの
判定は運営プレゼントと同じ `giftLog` なので、**既存の key を書き換えても
受け取り済みの人には届かない**。配り直しは新しい key で行うこと。

闇のオーラ解禁に合わせた `dk_shion`(シオン / ★3 / 闇)はここで配っている。
配布キャラは `giftOnly: true` を持ち、ガチャの排出プールからは外れる。

配布済みの一覧:

| key | 内容 |
|---|---|
| `gift_dark_debut` | 闇のオーラ解禁記念 — シオン(★3 / 闇) |
| `gift_x_launch` | X公開記念 — 💎45 |
| `gift_raid_kyuko` | 九狐降臨 実装記念 — 💎45 |

降臨ダンジョン「九狐降臨」とキュウコの定義・仮バランス・イラスト生成情報は [RAID_DESIGN.md](RAID_DESIGN.md) を参照。降臨キャラのみ開眼は最大10段階、段階ごとに必要な同キャラ数が増加し、効果は降臨キャラクターのドロップ率アップになる。通常キャラの開眼は従来通り4段階。

盤面サイズを変えない全画面セリフ・味方状態アイコンと生成プロンプトは [PLAYER_STATUS_UI.md](PLAYER_STATUS_UI.md) を参照。

### ログインボーナス・プレゼントボックス

フレポや運営プレゼントは所持数へ直接足さず、いったんプレゼントボックス
(`state.gifts`)に入れてからプレイヤーが受け取る。増えたことに気づかないまま
進む事故を避けるためで、ホーム右上の箱にバッジが出る。

ログインボーナスはその日はじめての起動で1つ入る。連続日数に応じて
`💰300 + 100×(日数-1)` と増え、`LOGIN_STREAK_MAX`(10日)で頭打ち。
5日ごとの節目には 💎2 が付く。前日にログインしていなければ1日目へ戻る。

### アカウント(ID / パスワード)

メールアドレスは入力させず、IDを実在しないドメイン(`.invalid` は RFC 2606 で
永久に予約済み)のアドレスへ変換して Firebase のメール/パスワード認証に渡している。

```
起動           匿名でサインイン(すぐ遊べる。uid にセーブが紐づく)
  ↓
マイページで登録  linkWithCredential で匿名アカウントを昇格
                → uid が変わらないので、セーブもフレンドも引き継がれる
  ↓
別端末          signInWithEmailAndPassword で同じ uid に戻り、
                クラウドのセーブでその端末を上書きする
```

登録に `createUserWithEmailAndPassword` を使ってはいけない。**新しい uid が
発行され、それまでのセーブが孤児になる。**

ID の重複チェックは Firebase が `auth/email-already-in-use` を返すため、
Firestore 側でユニーク制約を作る必要がない。ただし Authentication の
**Email enumeration protection** を有効にするとエラーが曖昧になり
「そのIDは使用済み」を出せなくなるので、その場合は別途 ID 予約用の
コレクションが必要になる。

**架空アドレスのためパスワード再設定メールは送れない。** 忘れると復旧できない
ことをマイページの登録欄に明示している。

### 管理者アカウント

`src/js/core/account.js` の `ADMIN_IDS` に入れたIDを管理者として扱う。現在は
`cadmium` のみ。

管理者への配布は同ファイルの `ADMIN_GRANTS` に並べる。`key` ごとに一度だけ
適用されるので、追加で配りたくなったら新しい `key` の行を足すだけでよい
(既存の `key` の数値を書き換えても再付与はされない)。現在の合計はオーブ1000。

付与済みフラグは `state.grants` に入り、クラウドセーブにも含めているので、
別端末でログインしても重複して付与されない。

**これはサーバで検証される権限ではない。** Cloud Functions を使わない構成では
クライアントの改変を防げないため、`ADMIN_IDS` は「誰が管理者か」を示す運用上の
目印でしかなく、不正防止の役割は持たない(そもそもローカル保存を書き換えれば
誰でも同じことができる)。管理者に実害のある操作を持たせる場合は、この前提が
成り立たないことに注意すること。

### フレンドでできること
- **プレイヤーアイコンは「フレンドに貸し出しているキャラクター」のアイコン**になる。
  トップバーのアイコンをタップすると所持キャラクター一覧から選び直せる。
  (以前あった絵文字を個別に選ぶ方式は廃止した)
- フレンドになる経路は2つ。
  - マイページで発行される「フレンドコード」を交換する
  - ダンジョンのサポートで**フレンド以外のプレイヤー**を借り、クリア後の
    確認から登録する(`fetchStrangerRentals()` が候補を拾う)
- **フレンドポイントの入手経路は2つだけ**。ダンジョン報酬・ショップ・
  フレンド登録ボーナスからは出さない。
  - 毎日1回の「あいさつ」: 自分+20、相手+10
  - **自分の貸し出しキャラが使われた回数 × 50 を翌日まとめて受け取る**
    - 借りた側が相手の `rentalUseCount` を +1 する
    - 持ち主は起動時、日付が変わっていれば未受取ぶんを受け取る
      (`rentalRewardedCount` と `lastRentalRewardDate` で二重取りを防ぐ)
- マイページの「貸し出しキャラクター」で1人を指定すると、フレンドの
  ダンジョン挑戦時にサポート枠として借りられる(リーダースキルも発動する)
